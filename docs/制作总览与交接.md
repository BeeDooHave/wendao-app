# 《问道》制作总览与交接

> 版本：M1 首次引气与雨痕反馈强化
> 更新日期：2026-05-27
> 用途：制作记录、新窗口接手、阶段验收与下一步排期

## 1. 项目定位

《问道》是一款把现实中的专注、学习、运动与休息，转写为修真叙事的离线 PWA。玩家并非靠点击获得修为，而是以真实完成的功课推动境界、环境与剧情变化。

核心体验承诺：

- 初次打开像踏入一场雨夜仙门故事，而不是注册一个任务工具。
- 灵根只提供身份与叙事差异，道途来自玩家选择，不设置天赋强弱焦虑。
- 修行允许很轻地开始，也允许低谷与中断；断签不惩罚人格。
- 重要变化必须由真实行为触发，演出不能假装玩家已经修成。
- 数据优先留在本机，隐私表述必须清楚胜过古雅。

一句话体验：**在一盏未熄的灯下，把现实中仍想守住的事，修成自己的道。**

## 2. 当前里程碑

### M1：入门仪式与首次入室

本阶段已形成可完整体验的开局流程：

1. 雨夜黑场字幕逐段推进，说明主角为何来到听雨山。
2. 山门显现，以「你想成为什么样的人？」收束序幕。
3. 闻钟先以灯火显形，再以全身画面和对话接引来者。
4. 玩家留下姓名或称呼，也可选择「暂不留名」，以「无名来者」入山。
5. 玩家在问心台自选灵根，或在测灵台离线排四柱，仅取日主五行作为游戏灵根。
6. 玩家选择剑、体、丹、符、阵之一道途。
7. 对应引路人以全屏过场现身，交谈后传授三卷初法。
8. 领受初法后，引路人身影隐入雨夜，余光引玩家进入静室。
9. 首页先作为「候行」场景显现；玩家确认开始今日修行后，修为与功课界面才露出。

此流程的关键原则是：**入室不等于完成修行**。首次引气与后续剧情仍必须等待玩家亲手完成现实功课。

## 3. 当前已完成内容

### 3.1 入门与身份

- 黑屏点击式序幕、山门结尾画面与叩门操作。
- 闻钟接引剧情、称呼登记与匿名入山路径。
- 问心台自选五行灵根与五条道途。
- 测灵台本地历法计算：展示四柱，只以日主映射游戏灵根。
- 首批推荐功法模板与引路人授法对话。

### 3.2 引路人与授法演出

- 闻钟及五位道途引路人的全身竖屏画面。
- 暗场中以灯火、法器或明确光源先行揭示人物。
- 所有引路人使用同规格全屏过场，不混入缩小人物副图层。
- 初次授法后加入「余光引路 -> 静室候行 -> 首页释放」过场。

### 3.3 修行系统

- 计时、数量、守约三类功法及统一修为折算。
- 今日功课调度、主修、重复日、拖动排序。
- 一分钟起念入口与养息日低门槛收束。
- 闭关计时、后台切出处理、完成结算与连续修行记录。
- 引路人求法入口已有本地体验形态；联网 AI 授法尚未接入。

### 3.4 首页、境界与剧情

- 首页盘坐修行场景及灯火、雨幕、书案、气息反馈。
- 炼气法相四阶段表现。
- 筑基法相方案与叠加资产已经接入，仍需进一步实机视觉确认。
- 推演沙盒，可预览状态而不污染真实存档。
- 「未熄之灯」剧情首卷的世界、人物与行为节点框架。
- 首次引气改为首门真实功课后才点亮稳焰、扩张灯照并显出灵根色回应的完整镜头。
- 雨痕退寸改为两不同实修日后窗棂刻度湿线从「二」退至「一」的明确参照表现。

### 3.5 声音、离线与数据

- 雨声、古琴、木鱼闭关声景与完成铜铃。
- PWA 离线缓存及本地 `localStorage` 存档。
- JSON 数据导入导出。
- 离线历法依赖随项目打包，隐私说明已保留直白表述。

## 4. 核心用户流程

### 4.1 首次进入

```text
打开 App
  -> 雨夜序幕字幕
  -> 山门初叩
  -> 闻钟接引并登记称呼
  -> 问心台 / 测灵台定灵根
  -> 选择道途
  -> 道途引路人显形与授法
  -> 余光引入静室
  -> 玩家主动开始今日修行
  -> 首页与真实功课循环
```

### 4.2 日常返回

```text
打开 App
  -> 首页环境承接上次真实进度
  -> 选择功课或一分钟起念
  -> 闭关 / 记录数量 / 确认守约
  -> 修为、环境和剧情节点回应
```

### 4.3 中断后归来

当玩家离开一段时间后，不以责备或损失作为第一反馈，而直接以大屏引导重新起念。目标是先重建行动，再恢复长功课节奏。

## 5. 叙事与文案定案

### 5.1 已定世界方向

- 山门：听雨山门。
- 主线意象：雨会冲淡念想，人的持守使灯未熄。
- 首位接引人：闻钟，守灯，也记录来者留下的名字。
- 玩家身份：入门来者，而非开局即有资格受道号之人。

详细设定见 [世界观与剧情设定.md](./世界观与剧情设定.md)。

### 5.2 用语规则

- 使用「姓名 / 称呼」，不使用「系统赐汝道号」。
- 初入山门默认称谓不可写成已经晋升的身份荣誉。
- 古意来自节奏、意象和克制，不来自让关键信息难懂。
- 隐私承诺必须明确写出：本机计算、不保存原始出生时间、不作现实命理解读。
- 不在演出中提前宣称玩家已完成修行、已引气或已获得真实成果。

### 5.3 已采纳的文案基调

- 「天赋为引，道途由心。道途不同，际遇自异；然修为深浅，终在己心。」
- 「闻钟展开灯册：来者，留下你的名字。」
- 「名字未必抵得住这场雨，却能让你记得，今夜为何上山。」
- 「真正的第一课，仍待你亲手开始。」

## 6. 技术实现摘要

### 6.1 技术形态

- 纯前端 PWA：`index.html`、`styles.css`、`app.js`、`sw.js`。
- 无后端账号系统；存档存于浏览器本地。
- 当前缓存版本：`wendao-v0.58-first-qi-rainmark`。
- 四柱计算依赖本地打包的 `vendor/lunar.js`，许可见 `vendor/lunar-LICENSE.txt`。

### 6.2 关键目录

| 路径 | 作用 |
|---|---|
| `assets/mentors/` | 闻钟与五位引路人全屏过场画面及概念图 |
| `assets/audio/` | 闭关声景和完成音效 |
| `assets/generated/` | 法相等生成型效果资产 |
| `docs/` | 制作、世界观、体验、美术与素材许可文档 |
| `vendor/` | 随应用离线使用的第三方依赖及许可 |

### 6.3 重要状态与兼容策略

| 状态 | 含义 |
|---|---|
| `identity` | 灵根、道途、称呼来源及可选四柱结果 |
| `storySeen` | 已观看的关键剧情节点 |
| `initiationSeen` | 是否看过首次受法后的入室演出 |

新增 `initiationSeen` 时，对旧存档默认视为已观看，避免既有玩家突然被强制重播开局过场；新入门玩家则只观看一次。

## 8. 下一阶段路线

### P0：本里程碑封版校验

- 在手机窄屏与较长屏幕上确认六位人物全屏裁切、灯光锚点和对话框不遮住关键面部/法器。
- 从全新存档完整跑一遍五道途，确认入室演出只在首次授法播放一次。
- 检查 PWA 离线重新打开、数据导出导入与旧存档迁移表现。

### P1：真实修行后的第一份叙事回报（本轮已接入）

- 「首次引气」仅由完整常规功课触发，首成镜头与首页长期状态共同显示灯芯由候火立为稳焰、暖光越过案沿与灵根回应。
- 「雨痕退寸」以窗棂刻度、湿线位置和灯照铺开构成前后对照，不再仅依赖雨幕透明度。
- 完善第一周七日节奏：轻量日、回归日与第一次长线承诺。

### P2：引路人求法与功法成长

- 设计 AI 引路人授法协议：玩家描述需求，引路人生成古意功法名、类型和合理修为折算。
- 明确 AI 不得诱导过度时长、不应对健康或命理作现实断言，并给玩家修改确认权。
- 将功法从「模板」扩展为可成长、可留下修炼记忆的个人技艺。

### P3：破境与长期世界

- 验证筑基视觉并制作金丹及后续境界资产。
- 制作筑基之约、突破文书和更明显的首页环境阶段变化。
- 扩写宗门人物关系、事件分支与机缘录。

## 9. 尚待决定的问题

- 「打卡功法」是否需要独立存在，还是由计时、数量、守约三类已充分覆盖日常记录。
- AI 引路人采用何种服务与费用策略，以及是否仅由用户主动开启联网能力。
- 是否提供「重温入门过场」入口，且如何与真实新档体验区分。
- 环境反馈在安静克制与明显奖励之间的最终力度。
- 数据同步是否始终保持可选且不破坏离线优先承诺。

## 10. 验收清单

### 开局与演出

- 新存档进入时先见序幕，不直接落到首页。
- 文案没有「系统赐道号」或不合资格的默认身份。
- 闻钟及五引路人均为单一全屏人物图层。
- 灯光与图片内光源在常见屏幕比例下对得上。
- 初次授法后存在入室承接，首页不会生硬闪现。
- 入室文本不误称功课已经完成。

### 行为与数据

- 一分钟起念可正常开始并按规则结算。
- 数量与守约功法不会重复发放修为。
- 中断归来可直接进入低门槛启动。
- 起念与养息不能误触发首次引气或雨痕退寸；第二个不同实修日才可使湿线退至上方刻度。
- 测灵台只保留必要结果，隐私提示清楚可见。
- 旧存档不会意外重新播放首次入室演出。

### 发布前

- JavaScript 语法检查通过。
- `git diff --check` 无空白错误。
- 本地预览可打开，关键 CSS、JS 和 Service Worker 资源可加载。
- 新存档及已有存档路径至少各手测一次。

## 11. 多模型制作流程与用量控制

Token 变多，主要不是因为项目做错了，而是长对话累积了大量已定事实、视觉尝试和反复校验。DeepSeek 的计费低，后续应让它承担更多可批量探索、可明确验收的前置工作；Codex 仍负责仓库落地、状态正确性和实际验证；Claude Opus 只在少量关键视觉门槛作高级审阅。

### 11.1 模型职责

| 工作 | 主力 | 交付物 | 最终验收 |
|---|---|---|---|
| 世界观扩写、剧情对白、章节分支 | DeepSeek | 3 至 5 套候选与自检意见 | 用户选择方向，Codex 接入 |
| 功法命名、引路人口吻、授法内容 | DeepSeek | 古意名称、类型建议、台词候选 | Codex 校验规则与产品边界 |
| 文案一致性和违和排查 | DeepSeek | 问题清单与修订稿 | Codex 对照设定文档确认 |
| 场景分镜、美术提示词初稿、角色设定卡 | DeepSeek | 镜头节奏、光源要求、提示词 | Codex / Opus 检查视觉可落地性 |
| 用户流程质检和边界场景枚举 | DeepSeek | 首次玩家、低谷玩家等视角报告 | Codex 复现并修正 |
| 代码、存档迁移、数值约束、离线能力 | Codex | 可运行实现和测试结果 | 浏览器与检查命令验证 |
| 关键过场、主视觉、整批角色最终审美把关 | Claude Opus | 一轮聚焦视觉评审 | 用户与 Codex 决定是否接入 |

### 11.2 应优先交给 DeepSeek 的任务

1. **剧情编剧室**：首次引气、雨痕退寸、七日守心、中断归来等节点，先产出多稿、人物口吻对照和是否误导玩家的自检。
2. **AI 引路人内容设计**：把玩家目标转换为功法名、计时 / 数量 / 守约类型、起念版本、正常版本与养息日版本的候选结构。
3. **批量审稿**：统一检查现代系统口吻、用词重复、过度晦涩、错误奖励暗示、人物失真及隐私说明是否足够清晰。
4. **体验陪审**：分别以首次玩家、低谷归来玩家、修真题材玩家和不愿输入生日的玩家视角检查流程。
5. **美术前置策划**：先写角色卡、镜头、光源位置、图像提示词和验收项，再投入图像生成或 Opus 视觉评审。

### 11.3 品质护栏

- DeepSeek 可大量起草内容，但必须遵守本文档、[世界观与剧情设定.md](./世界观与剧情设定.md) 和 [美术与演出指引.md](./美术与演出指引.md) 的已定规则。
- 修为数值、存档迁移、隐私承诺、健康相关措辞、联网权限与支付策略不得由模型自由决定；它只能给候选，代码和产品规则负责约束。
- DeepSeek 不直接大范围自由修改代码。其强项输出应为方案、文案、结构化数据或审查清单，由 Codex 接入代码并完成回归验证。
- 对明确的内容问题，优先让 DeepSeek 一次给出多个候选和推荐理由，而不是无限轮次地反复润色单稿。
- Opus 只用于影响整体观感的节点，例如新主界面、关键剧情过场、整套角色立绘定调；一般按钮、间距和局部 CSS 不重复消耗高价评审。

### 11.4 标准生产链路

```text
用户给出一个明确目标
  -> DeepSeek 先提供候选剧情 / 分镜 / 命名 / 审稿报告
  -> 用户或 Codex 依据既定规则选择方案
  -> Codex 修改代码、接入资产和状态触发
  -> Codex 在实际浏览器跑完整用户路径
  -> 仅当画面属于关键视觉节点时，交 Claude Opus 做最终评审
  -> 定稿后更新文档并提交
```

### 11.5 节省上下文的操作原则

1. **一阶段一提交**：每完成一个可体验闭环，就写入文档并提交；下一窗口只阅读文档、代码差异和当前目标。
2. **用文档代替历史聊天**：不要让新窗口重读所有讨论；本文件负责说明结论、边界和下一步。
3. **用截图代替宽泛描述**：视觉问题提供实际页面截图或具体过场节点，模型不必从头猜测。
4. **先定验收标准，再制作**：例如「灯光必须对准画面光源」「真实完成功课后才触发首次引气」。
5. **保持原型与定稿分层**：候选文案、概念图和推演结果可以低成本扩展；只有通过验收的内容才接入正式流程。

- docs/制作总览与交接.md

- docs/世界观与剧情设定.md
- docs/修行体验蓝图.md

本地预览：http://localhost:8437/

本轮目标：〔例如：强化“首次引气”剧情与画面反馈，让玩家在真正完成第一门现实功课后，明显看到灯火与静室发生变化。〕

协作规则：
1. 优先让 DeepSeek 参与可批量生成与审阅的工作：剧情候选、对白、功法命名、分镜、美术提示词、体验质检和一致性审稿。需要时让它一次提供 3 至 5 个候选，并给推荐理由。
